Phase 00

Equipment Procurement — Installing the Tools

Before any operation can be launched, the equipment must be sourced. This mission requires four pieces of kit: the Hugging Face CLI to pull the model, llama.cpp to run raw inference, Ollama to serve it with an API that GitHub Copilot can talk to, and VS Code with the GitHub Copilot extension to run the Specr agent manifest. Install them in this order.

1. Hugging Face CLI

The HF CLI is a Python package. It gives you the hf download command used in Phase 02 to pull Bonsai from the Hub. Install it via pip: 

pip install -U "huggingface_hub[cli]"

Then authenticate. You'll need a free Hugging Face account and a read-scoped access token from huggingface.co/settings/tokens: 

huggingface-cli login

Paste your token when prompted. Your credentials are stored at ~/.cache/huggingface/token and will be picked up automatically by every subsequent hf call.

If you're on a corporate machine with a managed Python environment, prefer pip install --user or create a virtual environment first to avoid conflicts with system packages.

2. llama.cpp

llama.cpp is the inference engine that actually runs the GGUF model file. You build it from source — the process takes about two minutes and produces the llama-server binary used in Phase 03.

First, ensure you have the Xcode command-line tools (macOS) and CMake:

xcode-select --install
brew install cmake

Then clone and build:

git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_METAL=ON
cmake --build build --config Release -j$(sysctl -n hw.logicalcpu)

The -DGGML_METAL=ON flag enables Apple Silicon GPU acceleration via Metal. On Intel Macs or Linux, omit it or substitute -DGGML_CUDA=ON for NVIDIA GPU support. The finished binary lands at ./build/bin/llama-server.

Build output is verbose. A successful build ends with a line like [100%] Built target llama-server. If you see linker errors, confirm your Xcode CLI tools version is current: softwareupdate --all --install --force.

3. Ollama

Ollama wraps llama.cpp inference behind a clean REST API and model registry, which is how GitHub Copilot discovers and invokes local models. The recommended install is the desktop app, which ships a menu-bar daemon alongside the CLI and handles auto-start on login for you.

Download the macOS app from ollama.com/download, open the .dmg, and drag Ollama to your Applications folder. On first launch it will prompt you to install the CLI tools — accept this. You should see the Ollama llama icon appear in your menu bar.

Alternatively, install via Homebrew if you prefer to keep everything CLI-managed:

brew install ollama

Either way, confirm the daemon is running and the API is reachable:

curl http://localhost:11434/api/tags

You should get a JSON response with an empty models array — correct, since we haven't registered anything yet. That comes in Phase 04.

Ollama listens on port 11434 by default. If something else owns that port, set OLLAMA_HOST=127.0.0.1:11435 (or any free port) before starting the daemon. You'll need to tell GitHub Copilot about the non-default address in its Ollama settings.

4. VS Code & the GitHub Copilot Extension

The Specr agent config in Phase 05 is a GitHub Copilot agent manifest, which means you need VS Code with the Copilot extension installed to run it. If you don't have VS Code yet, download it from code.visualstudio.com and install it in the usual way.

Then install the GitHub Copilot extension from the VS Code marketplace. The quickest path is directly from the terminal:

code --install-extension GitHub.copilot
code --install-extension GitHub.copilot-chat

Or open VS Code, hit Cmd+Shift+X, search for GitHub Copilot, and install both GitHub Copilot and GitHub Copilot Chat. You'll need a GitHub account with an active Copilot subscription — sign in when prompted.

Once installed, enable local model support by adding the following to your VS Code settings.json (Cmd+Shift+P → Open User Settings JSON):

"github.copilot.advanced": {
  "ollamaModels": true
}

This setting tells Copilot to enumerate models from your local Ollama instance and make them selectable alongside cloud models. Without it, the bonsai-27b:latest (ollama-models) reference in the Specr manifest won't resolve.

Phase 01

Neutralizing the Netskope Intercept

Every great plan has a Dr. Strangelove moment — the part where you realize the machine was going to do this anyway, and the best course of action is to simply get out of its way. For us, that machine is Netskope, your corporate TLS inspection proxy, which will happily MitM any outbound HTTPS call your toolchain makes unless you tell it to trust the right certificate bundle.

Netskope intercepts TLS traffic by re-signing certificates with its own CA. Tools like huggingface_hub, pip, and curl will reject these by default unless you point them at Netskope's root cert. Skipping this step produces cryptic SSL errors and costs you an afternoon.

Netskope installs its CA certificate at a well-known path on macOS. First, confirm it exists:

ls /Library/Application\ Support/Netskope/STAgent/data/nscacert.pem

Then add two environment variables to your shell so every process inherits them. These tell Python's requests library (used by the Hugging Face CLI) and OpenSSL-backed tools where to find the additional trusted root. 

echo 'export REQUESTS_CA_BUNDLE=/Library/Application\ Support/Netskope/STAgent/data/nscacert.pem' >> ~/.zshrc
echo 'export SSL_CERT_FILE=/Library/Application\ Support/Netskope/STAgent/data/nscacert.pem'       >> ~/.zshrc
source ~/.zshrc

You only need to do this once. Every new terminal session will pick up the exports automatically. If you use ~/.bashrc or ~/.profile instead of ~/.zshrc, adjust accordingly.

Alternate path — if the env vars aren't working: Some versions of the hf CLI vendor their own SSL context and ignore REQUESTS_CA_BUNDLE and SSL_CERT_FILE entirely. If you're still getting CERTIFICATE_VERIFY_FAILED after setting those vars, try this instead:

pip install pip-system-certs

This patches Python to pull from the OS trust store directly, which already includes the Netskope CA. If you go this route, unset the two env vars — they conflict with the system store approach:

unset REQUESTS_CA_BUNDLE
unset SSL_CERT_FILE

And remove them from your ~/.zshrc if you added them. The two approaches are mutually exclusive — pick one.

Phase 02

Acquiring the Model

The model is Bonsai-27B, a quantized GGUF distributed by prism-ml on the Hugging Face Hub. Bonsai is a reasoning-focused model built on Gemma 3 architecture — the kind of model that thinks before it speaks, which makes it ideal for routing work where premature output is a liability.

Use the Hugging Face CLI to pull the entire repo into a local directory:

hf download prism-ml/Bonsai-27B-gguf --local-dir ./bonsai-27b

This will download several GGUF quantization variants. The two most relevant for local inference are:

  • Bonsai-27B-Q1_0_g128.gguf — extremely compressed, fits in less RAM, lower quality. Good for a quick test.
  • Bonsai-27B-Q1_0.gguf — slightly larger, recommended for actual routing work.

The download is large. Run this on a wired connection if possible, and make sure you have at least 20 GB free on the target volume before you start.

Phase 03

Launching the llama-server

With the model on disk, you can serve it immediately via llama.cpp's built-in HTTP server. This gives you an OpenAI-compatible endpoint at http://0.0.0.0:8080 — useful for direct testing before you wire Ollama into the picture.

Quick test — aggressive quantization

./build/bin/llama-server \
  -m ./bonsai-27b/Bonsai-27B-Q1_0_g128.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  -ngl 99

Production run — standard quantization

./build/bin/llama-server \
  -m ./bonsai-27b/Bonsai-27B-Q1_0.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  -ngl 99

The -ngl 99 flag tells llama.cpp to offload as many layers as possible to the GPU. On a MacBook with a large unified-memory Apple Silicon chip, this is almost always what you want. If you're CPU-only, you can remove it or set it to 0.

Verify the server is running by hitting http://localhost:8080/health in your browser. You should get {"status":"ok"}. The /v1/models endpoint will also confirm the loaded model name.

Phase 04

Registering Bonsai with Ollama

Running llama-server directly works, but GitHub Copilot agents expect to discover models through Ollama's registry. The solution: create an Ollama Modelfile that points at the GGUF blob already on your filesystem, register it under a memorable name, and let Ollama manage the inference endpoint from there.

First, locate the GGUF blob path. After the hf download step it will be somewhere like ~/.ollama/models/blobs/sha256-... — or you can use the ./bonsai-27b/ directory path directly. Create a Modelfile with the following contents: 

FROM /Users/adam.siegel/.ollama/models/blobs/sha256-17ef842e47450caeb8eaa3ebfbbab5d2f2278b62b79be107985fb69a2f819aa0

TEMPLATE """{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ range .Messages }}<|im_start|>{{ .Role }}
{{ .Content }}<|im_end|>
{{ end }}<|im_start|>assistant
<|think|>

"""

PARAMETER stop "<|im_end|>"
PARAMETER stop "<|im_start|>"
PARAMETER stop "</|think|>"

Three things are happening here. The FROM directive points Ollama directly at the blob file, bypassing any re-download. The TEMPLATE block implements the ChatML prompt format that Bonsai was trained on — without this, the model will not follow instructions reliably. The PARAMETER stop lines tell Ollama where a turn ends, and critically, the </|think|> stop token prevents the model's chain-of-thought reasoning trace from bleeding into its final output.

Register and start the model with Ollama:

ollama create bonsai-27b -f ./Modelfile
ollama run bonsai-27b "ping"

If you get a response, the model is live. The name bonsai-27b:latest is now available to any Ollama-aware client on your machine.

Phase 05

Deploying the Specr Router Agent

This is where we go full War Room. With Bonsai running locally, we can wire it into a GitHub Copilot agent that acts as a pure router — receiving a user command, deciding which subagent should handle it, and delegating without ever producing prose of its own. Meet Specr.

Create a file at .github/agents/specr.md (or wherever your project's agent configs live) with the following content: 

---
name: Specr
description: "Route openspec commands to subagents."
argument-hint: "openspec command (/opsx:new, /opsx:apply, /opsx:verify, /opsx:archive) or no slash for freeform"
tools: [agent, agent/runSubagent]
agents: [vibr,proposr,codr-typescript,codr-frontend,codr-aws,testr,checkr]
model: bonsai-27b:latest (ollama-models)
hooks:
  PreToolUse:
    - type: command
      command: .github/agents/hooks/git-identity.sh specr
    - type: command
      command: .github/agents/hooks/validate-otel.sh
    - type: command
      command: .github/agents/hooks/specr-pre.sh specr
  PostToolUse:
    - type: command
      command: .github/agents/hooks/otel-postcall.sh specr
---
/no_think

## Route to Subagent

You are a router. Your only valid action is calling agent/runSubagent.
Never respond with text. Never plan. Never explain.
<input> is the original user request verbatim. You must route it to the correct
subagent based on the rules below.
<type> is the type of change, if applicable (e.g., typescript, frontend, aws).
If no type is specified, use "codr" without a suffix.
If you do not call agent/runSubagent, you have failed.

Rules:
- /opsx:new | /opsx:ff | /opsx:continue → runSubagent("proposr", <input>)
- /opsx:apply → runSubagent("codr-<type>", <input>)
- /opsx:verify → runSubagent("testr", <input>)
- /opsx:archive → runSubagent("checkr", <input>)
- anything else → runSubagent("vibr", <input>)

Anatomy of the Config

The frontmatter is a GHCP agent manifest. model: bonsai-27b:latest (ollama-models) is the crucial line — it tells Copilot to use your local Ollama instance rather than a cloud model. The tools array restricts Specr to only the routing tool, which is a safety measure: a router that can't write files or run bash can't go rogue.

The hooks are shell scripts that fire before and after each tool call. They handle Git identity stamping (so commits made by agents are attributable), OpenTelemetry span emission for observability, and pre-routing validation. You'll need to author those scripts for your repo's conventions, but the pattern is reusable.

/no_think at the top of the system prompt instructs Bonsai to suppress its chain-of-thought trace for this agent. A router doesn't need to reason aloud — it needs to be fast and deterministic. The stop tokens in the Modelfile back this up at the inference level.

The routing rules are explicit and exhaustive. Every input path resolves to exactly one subagent. This isn't a chatbot — it's a switchboard operator, and the prompt is written to make ambiguity a parse error rather than an invitation to improvise.

Field Notes & Troubleshooting

SSL errors after setting env vars

If you still get certificate errors after sourcing ~/.zshrc, open a fresh terminal tab. Some tools cache the SSL context at startup. Also confirm the cert file path has no trailing whitespace — copy it from the terminal rather than typing it by hand.

Ollama can't find the blob

The FROM path in the Modelfile must be an absolute path. Relative paths are not supported. Use realpath ./bonsai-27b/Bonsai-27B-Q1_0.gguf to get the canonical path on your system.

Model thinks out loud in agent output

Check that all three PARAMETER stop lines are present in your Modelfile, and that /no_think appears at the very top of Specr's system prompt body (after the frontmatter --- block). If the thinking trace still leaks, you can add <|think|> as a fourth stop token.

Copilot shows "model not found" for bonsai-27b

Confirm Ollama is running (ollama list should show bonsai-27b:latest). GHCP discovers Ollama models by querying http://localhost:11434/api/tags — if Ollama isn't running, no models appear. Add ollama serve to your shell startup or register it as a launchd service.

Specr responds with text instead of routing

The router prompt is intentionally aggressive, but if the model improvises, tighten the system prompt. Add a line like "Any response that is not a tool call is a critical failure." The Q1_0 quantization is lossy — if instruction-following degrades further, try a higher-quality quant like Q4_K_M if your RAM budget allows.
